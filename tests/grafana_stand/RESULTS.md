# Grafana alerting stand: results

A disposable local Grafana stand on the developer's Mac, used to check the SORA
alert rules and the datasource provisioning. Not run in CI. No connection to the
project's database, compose stacks or volumes, and no contact with production.

Admin password: a throwaway generated by `stand.sh`, kept in `~/.sora-gstand/`
outside the repository. It appears nowhere in this file.

## Scenario B: migration from the original main provisioning

The original `origin/main` provisioning has two datasource files and no uid.
Extracted with `git archive origin/main grafana/provisioning`.

### B1, original provisioning, fresh volume

`GET /api/datasources`:

```json
[{"id": 1, "uid": "PBFA97CFB590B2093", "name": "Prometheus", "type": "prometheus",
  "url": "http://prometheus:9090", "isDefault": false, "orgId": 1}]
```

Log: `inserting datasource from configuration name=Prometheus uid=PBFA97CFB590B2093`.
The auto-generated uid is the production uid, and `isDefault` is false, matching
production. Five rules, all `datasourceUid: prometheus`, which resolves to no
datasource.

### B2, switch to a uid-`prometheus` file: FAILED

The repository's first candidate changed the uid to `prometheus`. Grafana 13.2.3
did not start:

```
logger=provisioning level=error msg="Failed to provision data sources"
    error="Datasource provisioning error: data source not found"
logger=backgroundsvcs.managerAdapter level=error msg="Module failed" module=provisioning
    err="... Datasource provisioning error: data source not found"
```

The container exited with status 1. A provisioned uid change is not an in-place
update: provisioning looks the existing datasource up by the new uid, does not
find it, and fails. Production with that file would have crash-looped on deploy.
The stand refused the uid rename; the migration plan in the review (update in
place to `prometheus`) is therefore false for this image.

### B3, switch to the existing uid (`PBFA97CFB590B2093`), same volume

`GET /api/datasources`:

```json

  "url": "http://prometheus:9090", "isDefault": true, "orgId": 1}]
```

Same id (1), uid unchanged, `isDefault` updated from false to true in place. The

## Deviations from the brief

1. **Datasource uid kept as `PBFA97CFB590B2093`, not `prometheus`.** The brief
   asked for uid `prometheus`. B2 measured that this cannot be applied to the
   existing production datasource: Grafana 13.2.3 fails with `data source not found`
   and exits. The repository keeps the production uid. The only other route to
   `prometheus` is `deleteDatasources` followed by re-creation, which changes the
   internal id on every start, so it cannot satisfy "restart again, no change".
   Rules reference `PBFA97CFB590B2093`, and the tests pin it.
2. **`prometheus.yml` deleted** as the brief said. The two files applied in turn and the
   second set `isDefault` false; that is the production state B1 reproduces.
3. **`up == 0` replaced** by `up{job="sora-app"}` with a `lt 1` threshold. The old
   form returned the value 0, which Grafana reads as Normal. The app-down rule
   fires on a down target (A2, 23:41:20).
4. **Stale rule uses `absent(...) * 1e9 or time() - ...`** so an absent gauge reads as a huge age
   and crosses 900. A bare `absent()` returns 1 and would stay Normal.
5. **Retrain-stale expression is a sum of two `bool` comparisons** so that it is 0 when
   healthy, including the -1 sentinel. A plain comparison drops the series.
6. **Gap rule noData OK, stale rule noData Alerting, app-down noData Alerting.** The stale
   rule cannot return NoData under its expression unless Prometheus returns nothing at
   all, so Alerting is the conservative choice there.
7. **`stand.sh override` shortens holds and the evaluation interval** for drive runs.
   The real-interval first evaluation (A1, A2) used the repository values.
8. **No contact point was configured**, so no notification delivery was tested. That is
   outside the stand's scope and remains open.

## Round 2: original interval and holds, no shortening (scenario C)

Run on a fresh volume with the repository provisioning exactly as committed
(`group interval 5m`, real `for:` holds, no override). Evaluations ran at the
5-minute group interval, aligned to 05:29:30, 05:34:30 and so on, UTC.

Starting conditions, t0 = 05:26:43Z: sora-app up; `drift_on=1`,
`rejected_on=1` (each sora-app scrape adds one to the counter);
latency histogram receiving 10 observations per scrape at 900 ms;
coverage success timestamp 1000 s old; `retrain_since=1300000` (over 1209600).

Timeline (driver log, `timeline-c.log`):

| UTC | event |
|---|---|
| 05:26:43 | t0: conditions above |
| 05:41:43 | t0+15m: counters stop; latency back to 50 ms |

| 06:51:43 | t0+85m: driver done |

Transitions (watcher log, `watch-c.log`, from the evaluator, one line per change):

| rule | Pending | Alerting / firing | Normal again | Notes |
|---|---|---|---|---|
| sora-drift-detected | (none, 0s hold) | 05:29:30 (first eval) | 05:49:30 | counter stopped 05:41:43; Normal 8 min later when the 5 min `increase` window cleared |
| sora-retrain-failed | (none, 0s hold) | 05:29:30 (first eval) | 05:54:30 | same counter mechanism, rejected |

Wall times of the Pending to Alerting transitions on the original interval and
holds: coverage-stale 45 min, retrain-stale 15 min, high-latency 5 min,
app-down 5 min. The hold for latency and app-down is shorter than the interval,
so the next evaluation sets Alerting.

Post-vanish states (06:49:30 eval, before restore): app-down Alerting (NoData);
drift, latency, retrain-failed and retrain-stale Normal (NoData), because their
series are no longer scraped and NoData resolves to OK for those rules by design.

Post-restore states (06:54:30 eval): every rule Normal, `lastError` empty.

### Interrupted attempt, not used for any result

The first round-two attempt ran at 00:11:55 UTC. The Mac slept during the first
900-second wait. The driver did not progress, Grafana's evaluation clock and the
host clock diverged, and the watcher exited early, so the timeline is not a
valid measurement. It was stopped and the stand was torn down. The rerun above
used `caffeinate` to keep the host awake and started from a clean stand.

### Reproduction

The historical timeline driver was a shell script kept outside the repository, with the
timeline above as its sleeps and `stand.sh control` calls. It is not committed:
it hard-codes the worktree path. The stand files in the repo (`stand.sh`,
`metrics_server.py`, `stand-prometheus.yml`, `check.py`) are what it drove
(the Prometheus file was subsequently renamed).

A new portable driver and guarded `stand.sh control` operation are documented in
`SCENARIO_C.md`. Their offline tests establish ordering and refusal, not a repeat
of the runtime results above. The historical external driver remains unavailable;
this follow-up does not retroactively make that original run fully reproducible
or prove notification delivery.
