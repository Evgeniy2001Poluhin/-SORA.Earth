# Надёжность и наблюдения: проверка и действия

Проверено 2026-11-06. Эта инструкция не даёт разрешения менять прод.
Хост: `109.120.147.12`; SSH только ключом. Не использовать старый alias `sora`.

## Снять состояние без изменения сервисов

Из корня проверенной рабочей копии:

```bash
ssh -o BatchMode=yes -o IdentitiesOnly=yes -o ConnectTimeout=10 \
  -i ~/.ssh/id_ed25519 root@109.120.147.12 python3 - \
  < scripts/platform_readiness_snapshot.py > /tmp/sora-readiness.json
```

Команда выполняет только чтение и создаёт JSON на машине оператора.
Сборщик не открывает дампы, пароли, записи проектов или журналы приложения.
Его успешный exit означает получение отчёта, а не общий GO: нужно отдельно
проверить `checks`, HTTP-коды и поля `not_verified` / `not_checked`.
Исчезнувшая серия, ошибка Prometheus, NaN или две серии вместо одной дают
`unknown`, а не зелёный результат.

## Если сайт недоступен

1. Записать UTC-время обнаружения, внешний HTTP-код, SHA и состояние backend,
   scheduler, nginx, postgres. Проверить с независимой сети: сбой VPN оператора
   не равен остановке сервиса. Не выводить `docker inspect` целиком: там секреты.
2. Проверить журнал деплоя, наличие deploy-процесса, lock и мигратора **чтением**.
   Не удалять `in-progress`, не освобождать lock и не запускать второй deploy.
3. Сверить фактическую ревизию Alembic с манифестом. Ожидаемая после ownership —
   `b7d41f2e9c35`. Не откатывать схему и не удалять `users` для запуска старого кода.
4. Выбрать fix-forward либо совместимый post-ownership релиз. SHA должен быть
   проверенным предком `origin/main` и пройти все барьеры скрипта. Сам факт
   наличия старого образа не делает его допустимым откатом.
5. Получить отдельный GO с хостом, SHA, способом восстановления и присутствием
   владельца. Выполнять только `scripts/deploy_production.sh`; не подменять
   процедуру ручным `compose up/restart`.
6. Проверить внешние health/ready, состояние БД, SPA и разграничение доступа;
   записать время восстановления. RTO считать от обнаружения до доступности,
   включая согласование и CI, а не только время `pg_restore`.

Источник уроков: `docs/incidents/2026-11-05-ownership-cutover-docker29.md`.
Дефект распознавания Docker 29 исправлен; обещание восстановления за 133 секунды
из репетиции не является измеренным временем аварийного восстановления.

## Проверка восстановления на отдельном стенде

Уже принятая репетиция реального дампа от 2026-11-05 не запускается повторно
автоматически. Для новой проверки необходим отдельный ресурсный план:
уникальные контейнеры и сеть, отсутствие опубликованных портов, ограничения
CPU/RAM, срок завершения и уборка только своих объектов. На проде — отдельный GO.

Критерии: checksum входа, восстановление в пустую временную БД, схема/ограничения,
счётчики и fingerprint, bootstrap, старт приложения, чтение сохранённой оценки
и изоляция аккаунтов. Фиксировать длительность всех стадий и отсутствие остаточных
контейнеров/томов. Восстановление с того же диска не доказывает восстановление
после полной потери сервера.

## Что наблюдать в накоплении

Контролируемый набор сейчас только `openmeteo / temperature`: 21 объявленная
точка. «Нет пропусков» относится только к нему, а не ко всем источникам.

- Завершённые UTC-дни: `[max(today − 30 дней, 2026-10-11), today)`.
- Нормальный точко-день: не менее 19 различных часов из 24. Несколько строк
  за один час не восполняют пропущенные часы. Полностью отсутствующая точка
  должна остаться в знаменателе.
- Проверять одновременно число пропусков, число дней, число точек и время
  последнего успешного расчёта. Старый ноль без свежей метки не доказывает здоровье.
- `gap` выше 0 держится 30 минут до предупреждения. Для `stale` возраст
  последнего успеха выше 900 секунд или отсутствие серии держится 45 минут.
  Группа оценивается раз в 5 минут, поэтому доставка не обещается ровно на границе.

При предупреждении: установить конкретные дни/точки, отличить пропуск источника
от сбоя ingestion и неудачного расчёта покрытия. Не переписывать историю и не
сдвигать начало окна, чтобы скрыть дыру. Повторный сбор, если возможен, должен
сохранять происхождение и время доступности; прогнозные метрики пересчитываются
по принятому протоколу M3, а не обещаются по одному зелёному gauge.

## Доставка уведомлений — отдельный открытый критерий

Правила в файле и состояние Alerting в Grafana не доказывают, что человек
получил уведомление. Для завершения нужны выбранный владельцем получатель и
канал, согласованный тест доставки и подтверждение получения/восстановления.
Секреты вводятся владельцем в хранилище сервиса и не передаются в чат.

Безопасный порядок: проверить contact point и route в интерфейсе Grafana;
по отдельному согласованию отправить тест получателю, затем на **изолированном
стенде** проверить переход Normal → Pending → Alerting → Normal с тем же маршрутом.
Не останавливать production scheduler и не портить реальные наблюдения ради теста.
До подтверждения доставки статус остаётся «не проверено».

## Полная потеря хоста — отдельный открытый критерий

Нужно согласовать внешнее хранилище, допустимую потерю данных и хранителя ключа
восстановления. Приватный ключ не хранить на бэкапируемом хосте.
Реализация `BACKUP_AUTOMATION.md` уже есть; установка требует настроек владельца.
Приёмка: завершённый внешний manifest, checksum, расшифровка на другом стенде,
восстановление и сверка fingerprint, а не только успешная выгрузка.
