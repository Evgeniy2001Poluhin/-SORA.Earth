# Резервные копии на MSI: план установки и приёмки

Дата: 2026-11-06. Статус: **получатель и ключи подготовлены, сквозной
синтетический restore прошёл; регулярное копирование не включено**.
Владелец предложил MSI как хранилище. Проверено только чтением: на C: свободно
304 460 988 416 байт (около 283,6 GiB). Это отдельный компьютер относительно VPS,
но он не является круглосуточно доступным облачным хранилищем.

## Предлагаемая схема

Пакет установки и порядок приёмки: `MSI_BACKUP_INSTALL.md`. На Mac уже создан
ключ восстановления; его вторая копия ожидает подключения флешки владельцем.
На MSI подготовлен отдельный ключ доступа, приватная часть осталась на MSI.
На VPS изменения не устанавливались, расписание MSI выключено.

1. После успешного локального ночного бэкапа сервер готовит зашифрованный
   экспорт. Новую криптосхему не изобретать: использовать существующий формат
   `scripts/backup_crypt.sh` / `backup_crypt.py` с его тестами и явными
   ограничениями из `BACKUP_AUTOMATION.md`.
2. На VPS находится только публичный ключ шифрования. Приватный ключ
   восстановления остаётся у владельца вне VPS. Владелец выбрал Mac и отдельную
   флешку; наличие копии на флешке ещё не подтверждено. Не пересылать ключ в чат
   или модели. Генерация постоянного ключа и проверка его двух копий — отдельный
   шаг установки, не выполненный этим документом.
3. MSI сам инициирует получение завершённого набора по SSH. Не открывать порт
   MSI в интернет и не давать VPS право удалять архивы на MSI.
4. Использовать отдельный ключ для получения бэкапов, не root-ключ владельца
   и не ключ MSI worker. На сервере ключ имеет только ограниченную команду
   чтения экспортного каталога. Нужны строгая проверка имени/пути и запрет
   shell, forwarding, PTY и доступа к исходным незашифрованным дампам.
   Один `sftp -d` без chroot не является изоляцией каталога.
5. Принимать файлы в `C:\Users\poluh\.sora-backups\incoming`, а затем атомарно
   публиковать завершённый набор в `completed`. Архивы и ключи не помещать в
   `.sora-worker`, `.sora-code`, промпты моделей или рабочую копию Git.

Серверная часть этой схемы меняет прод. До её выполнения необходим отдельный
GO на установку экспортёра и ограниченного ключа. Подготовка плана не даёт GO
на деплой приложения, изменение схемы БД или остановку сервисов.

## Расписание и хранение

- Основное получение: 04:00 UTC (07:00 МСК), после бэкапа 03:30 UTC.
- Повтор после входа/запуска MSI и периодически, пока нет свежего набора;
  только один процесс одновременно. Необязательную фоновую работу Ollama
  не использовать для принятия решений о копировании.
- При сне/выключении MSI копирования нет. После пропуска показывать фактический
  возраст последней завершённой копии, не обещать соблюдение RPO.
- Начальное предложение удержания: последние 28 ежедневных и 8 недельных
  наборов; совпадающие наборы считать один раз. Политика требует согласования
  владельца, а не включается автоматически этим документом.
- Удалять старое только после появления проверенной новой копии. Неполный
  или повреждённый набор не даёт права очищать последнюю хорошую копию.
- Контролировать свободное место до начала; при нехватке прекращать загрузку
  с явной ошибкой. Текущий дамп около 6 MB; расчёт вместимости не считать
  прогнозом роста данных или достаточным основанием отключать контроль места.

## Завершённый набор

Набор должен содержать версию формата, идентификатор БД, UTC-время создания,
ревизию Alembic и точные имена/размеры/SHA256 зашифрованных частей. Manifest
публикуется последним. Только проверенный manifest плюс все его части дают
статус «получен». Fingerprint реальных данных тоже чувствителен: не хранить
его в открытом виде, включать в зашифрованный материал.

SHA256 выявляет повреждения при передаче, но сам по себе не доказывает
подлинность изменённого вместе с архивом manifest. Доверие к источнику требует
закреплённого SSH host key; криптографическая целостность проверяется при
расшифровке существующего envelope. Не отключать StrictHostKeyChecking.

### Что остаётся проверить при установке

Сначала синтетический архив и изолированная временная БД:

| Проверка | Требуемый результат |
|---|---|
| Успешная передача | Все размеры/SHA256 совпадают, набор опубликован один раз |
| Повтор задания | Нет повторной загрузки и потери предыдущего набора |
| Обрыв соединения | Набор остаётся неполным, последняя хорошая копия сохранена |
| Отсутствие/изменение части | Ошибка; такой набор не публикуется |
| Подмена пути / `../` / symlink | Отказ экспортёра и получателя |
| Подмена host key | Соединение отклоняется |
| Нет места / доступ запрещён | Явная ошибка, удержание хороших копий |
| Сон и повторный запуск | Возобновление/безопасный повтор, без двойного процесса |
| Неверный ключ / повреждённый шифротекст | Отказ до восстановления |
| Восстановление | Расшифровка, restore и fingerprint совпадают на отдельном стенде |
| Очистка | Только временные объекты теста; production и worker не изменены |

После синтетической проверки — отдельная приёмка одного настоящего бэкапа
на изолированном стенде с согласованным доступом к данным. Полное восстановление
не проводить на рабочей БД. Секреты, сырые данные и fingerprint не включать в
общедоступный отчёт; достаточно идентификатора набора, хешей шифротекста,
результатов проверок и измеренного времени.

До фактического получения и восстановления статус защиты от потери VPS
остаётся «не подтверждена». До выбора канала тревог контролировать статус
можно вручную, но это не считается автоматической доставкой предупреждений.
