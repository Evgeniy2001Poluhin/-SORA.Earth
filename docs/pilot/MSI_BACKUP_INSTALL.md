## Доказательства подготовки

`tests/test_backup_transport.py` проверяет завершённость, повтор, порчу,
прерывание, отсутствие места, перекрытие, запрет путей/ссылок и сохранение
старой хорошей копии. Реальный encrypt → pull → decrypt проверен с существующим
`backup_crypt.sh`, без новой криптосхемы.

На самом MSI проверены бинарные файлы на NTFS через WSL, повтор без скачивания,
блокировка параллельного запуска и обнаружение испорченной копии.
Синтетический PostgreSQL-дамп зашифрован на Mac, принят получателем MSI,
возвращён на Mac и восстановлен в отдельном PostgreSQL 16 без сети/портов:

Дополнительно установщик проверен в отдельном Debian-контейнере без сети:

Сам `systemctl` в контейнере был явно заменён заглушкой: активация службы и
ограничения cgroup на настоящем systemd-хосте пока не проверены.

## Шаг владельца: вторая копия ключа

Когда флешка подключена, выбрать её реальный путь под `/Volumes/`. Скопировать
`recovery.pem`, `recipient.pem` и `public-key.sha256` в отдельную папку флешки.
Не отправлять эти файлы в чат, почту или модели.

На Mac проверить две копии:

```bash
bash scripts/verify_backup_recovery_key.sh \
  "$HOME/.local/share/sora-backup/recovery-20261106/recovery.pem" \
  "/Volumes/ИМЯ_ВАШЕЙ_ФЛЕШКИ/sora-backup/recovery.pem"
```

Путь флешки заменить фактическим; скрипт не копирует и не показывает ключ.
Он проверяет два разных файла и совпадение публичных частей. Факт, что второй
файл действительно находится на выбранном внешнем физическом устройстве,
нужно проверить отдельно. После проверки флешку безопасно извлечь и хранить
у владельца. До этого защита от потери Mac не подтверждена.

## Отдельный GO на сервер

Хост `109.120.147.12`. Устанавливаются только:

- новый системный пользователь/группа `sora-backup-reader`;
- root-owned `/usr/local/lib/sora-backup` с транспортом и существующей криптобиблиотекой;
- `/etc/sora-backup/recipient.pem` — публичный ключ;
- домашний каталог reader с публичным SSH-ключом и `restrict,command=...`;
- `/var/lib/sora-backup-export` — только зашифрованные версии;
- новые `sora-backup-export.service` и `.timer`.

Существующие приложение, схема, локальный бэкап, SSH daemon config и его
root-ключи не меняются. Установка не является деплоем приложения.
Перед GO проверить хеши пакета; в нём не должно быть `recovery.pem` или
`pull_ed25519` без расширения `.pub`.

Из корня проверенного пакета, сначала только проверка:

```bash
bash scripts/install_backup_export.sh --check recipient.pem reader.pub
```

Владелец отдельно разрешил продолжать без флешки (2026-11-06). Вторая копия
остаётся открытым пунктом, но больше не блокирует подготовку и согласование
установки. До появления второй копии ключ доступен только на Mac.

После отдельного GO на серверную установку:

```bash
bash scripts/install_backup_export.sh --apply recipient.pem reader.pub
systemctl start sora-backup-export.service
```

Экспортёр читает самый новый завершённый dump и его checksum. Проверяет возраст
до 26 часов, целостность и свободное место; создаёт зашифрованный tar с дампом
и метаданными. Частичный результат не публикуется. Автоудаления нет.
Порог 8 GiB шифротекста и ограничения памяти являются явными границами этой
первой установки; рост данных требует новой проверки ресурсов.

Расписание: локальный дамп 06:30 МСК, экспорт 06:45 МСК, получение MSI 07:00 МСК,
повтор каждые 30 минут и после входа пользователя. Используются UTC-таймеры
сервера, Windows переводит время в свою локальную зону.

## Приёмка после серверной установки

1. Убедиться, что unit успешен, manifest завершён, нет открытого plaintext в
   экспортном каталоге; reader не может читать `/var/backups/sora` и писать export.
2. С MSI проверить `list`, `manifest ID`, `part ID NAME`. Попытки `id`, shell,
   обхода каталога и forwarding должны быть отклонены. Не выводить данные архивов.
3. Однократно запустить `run_msi_backup.ps1`. Сверить размеры/SHA256 и статус.
4. Получить **одну настоящую** зашифрованную копию на Mac. Расшифровать только
   в новую защищённую папку; открыть существующую папку скрипт откажется:

   ```bash
   python3 scripts/backup_transport.py restore-files \
     --backup /ПУТЬ/К/ЗАВЕРШЁННОМУ/ID \
     --identity "$HOME/.local/share/sora-backup/recovery-20261106/recovery.pem" \
     --output /НОВАЯ/ЗАКРЫТАЯ/ПАПКА \
     --crypto-python /ПУТЬ/К/PYTHON_С_CRYPTOGRAPHY
   ```

   Это восстанавливает файлы, а не БД. Для `pg_restore` нужен отдельный
   согласованный временный PostgreSQL; рабочую БД не использовать. Принимать
   схему, ограничения и возможность чтения приложением. Checksum доказывает
   целостность копии, не корректность бизнес-данных в исходной базе.
5. Только после приёмки включить `install_msi_backup_task.ps1 -Apply`.
   Проверить LastTaskResult и фактическую новую копию после первого триггера.
6. Проверить вход после выключения MSI и догон пропущенного получения. Жёсткое
   прерывание может оставить незавершённую папку в `incoming`: она не считается
   бэкапом, повтор загружает в новую папку. Её очистка — отдельно, только своих
   временных файлов, после проверки, что получатель не работает.

## Если нужно остановить новую систему

Отключить только `SoraEncryptedBackupPull` на MSI и только
`sora-backup-export.timer` на VPS. При необходимости остановить его активный
service. Не удалять ключ восстановления, существующие копии, аккаунты/дампы
приложения или старый `sora-backup-local.timer`. Незавершённую установку
разбирать по созданным новым объектам; installer специально отказывается
перезаписывать существующий аккаунт и каталоги.

Пока владелец отложил канал тревог, автоматическая доставка человеку не
настроена. Ручная проверка получателя:

```bash
python3 scripts/backup_transport.py status --root /ПУТЬ/К/archives
```

Она проверяет последний завершённый зашифрованный набор и его возраст,
но не расшифровывает его и не доказывает, что предупреждение кто-то получил.
